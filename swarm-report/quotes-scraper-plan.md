# quotes-scraper — план лабораторной 1

Дата: 2026-11-20. Редакция CI уточнена пользователем после реализации этапа 3.
Фактические результаты реализации и незакрытые критерии — в build/review-отчётах.

## Summary and original request

Запрос: составить план первой лабораторной по `.memory-bank/lab-1.md`, slug
`quotes-scraper`. Все команды проекта должны выполняться через Makefile:
`build` — сборка образа; `run` — запуск с сохранением `out/result.json` на хосте;
`clean` — удаление образа и `out/` с сохранением кеша сборщика;
`ci` — сборка, запуск и проверка результата.
Публичные цели Makefile: build, run, clean, ci, lock и help. Диагностические
цели не требуются; проверка наличия образа выполняется прямо в рецепте run.

Уточнение процесса: сначала контейнерная среда и make build/run, затем
`src/scraper.js`, затем clean/ci/workflow/README и проверка всех восьми пунктов DoD.
Node.js, Playwright и Chromium устанавливаются и выполняются только в контейнерах.
На хосте нужны Docker и Make; исходники редактируются на хосте.

Источник требований — `.memory-bank/lab-1.md`.
Существующие пользовательские изменения сохранять. Эта редакция заменяет прежний
порядок и решения о способе разработки; требования лабораторной не изменяются.

Текущая проверенная ветка — `feat/quotes-scrapper`. Это написание требуется для
PR; slug отчётов намеренно отличается: `quotes-scraper`.

Решения плана, а не дополнительные требования задания:

- Node.js 22, JavaScript ESM и Playwright Chromium; совместимую точную версию
  зависимости проверить при реализации и закрепить в lockfile.
- Результат — массив `{text: string, author: string, tags: string[]}`;
  text/author непустые. Обойти всю доступную ленту, убрать повторы по паре
  text/author, сохранить порядок первого появления.
- Единственный сценарий разработки и запуска — контейнерный. На хосте нужны
  Docker и Make; npm, Node.js, Playwright и Chromium работают внутри контейнеров.

## Acceptance criteria

1. Chromium открывает `https://quotes.toscrape.com/scroll`, получает цитаты после
   выполнения JavaScript и подгружает хотя бы следующую порцию прокруткой.
   Обход завершается по подтверждённому сигналу конца, а не по произвольной паузе.
2. Успешный запуск создаёт непустой валидный `out/result.json` указанной схемы.
   Ошибка сети, разбора или таймаут дают ненулевой exit; браузер закрывается.
   Частичный результат не публикуется как успешный.
3. `make build` собирает один конечный образ multistage Dockerfile на
   `node:22-bookworm`. Chromium и системные библиотеки устанавливаются
   самостоятельно; готовые Playwright-образы не используются.
4. `make run` использует собранный образ, создаёт host-каталог `out/`, монтирует
   его в контейнер и сохраняет результат именно на хосте. Завершённый контейнер
   удаляется автоматически. Отсутствующий образ приводит к ясной ошибке.
5. `make clean` адресно удаляет образ проекта и `out/`, включая повторный вызов
   при их отсутствии. Кеш сборщика и чужие ресурсы сохраняются; реальные ошибки
   удаления не подавляются.
6. `make ci` последовательно выполняет сборку, запуск скрапера и проверку
   результата Node.js внутри контейнера. Отдельный набор тестов и цели test/
   verify-result сейчас не требуются. Порядок сохраняется при `make -j ci`;
   ошибка любого этапа останавливает последующие и возвращается вызывающей среде.
7. После `make clean` повторный `make build` использует кеш Chromium.
   Однострочная правка исходника не повторяет установку npm-зависимостей,
   системных библиотек и браузера. Доказательство — логи `CACHED` тяжёлых слоёв.
8. GitHub Actions вызывает `make ci`; README описывает проект, настройку
   локальной среды, сборку и запуск production-образа через make.
9. `out/`, зависимости и временные артефакты исключены из Git и Docker context.
   После clean нет новых артефактов в статусе Git. Полностью чистый статус
   проверяется на закоммиченном состоянии, без удаления пользовательских правок.
10. Полный DoD лабораторной дополнительно требует открытый, не слитый PR
    `feat/quotes-scrapper` → `main` и зелёный CI на последнем SHA PR.
    Публикация изменений текущим запросом не разрешена.

## Ordered steps and cross-layer dependencies

### 1. package.json, контейнерный lockfile, Dockerfile и make build/run

Создать ESM-манифест с закреплённым Playwright и командой запуска
`node src/scraper.js`, ignore-файлы и Makefile. Первой вспомогательной целью
`make lock` генерировать `package-lock.json` командой npm в одноразовом контейнере
`node:22-bookworm` с bind mount репозитория. Эта цель не зависит от ещё не
собранного образа приложения и не требует существующего lockfile. На хосте
появляется только lockfile; npm-кеш и установленные пакеты остаются в контейнере.
Проверить права владельца генерируемого файла на Linux. Все команды проекта
доступны через шесть публичных целей Makefile; ручных Docker/npm-команд нет.

Создать multistage Dockerfile: browser-base на `node:22-bookworm`, сначала
манифесты и `npm ci`, затем установка Chromium с системными библиотеками через
CLI закреплённого Playwright. Зафиксировать `PLAYWRIGHT_BROWSERS_PATH`.
Финальную стадию наследовать от browser-base, копировать исходники после тяжёлых
слоёв. Системные библиотеки должны оставаться в конечном образе; браузер при
запуске не скачивается. Версию Playwright проверить по официальному источнику
при реализации. `.dockerignore` исключает out, node_modules, Git и служебные файлы.

Добавить рабочие `make build` и `make run`: стабильное имя образа, абсолютный
host-путь out, bind mount и `--rm`. Убедиться в правах на результат на Linux.
Чтобы образ собирался до написания скрапера, финальная стадия копирует существующий
каталог `src/` с отслеживаемым `.gitkeep`, а не отсутствующий scraper.js.
`run` пока ожидаемо завершается ненулевым кодом из-за отсутствия скрапера;
фиктивный результат или успешную заглушку не создавать. На этом этапе проверить
сборку и рецепты запуска; функциональный успех run проверяется после этапа 2.

Выход этапа: lockfile создан контейнерной make-целью, браузерная среда собрана,
build/run подготовлены. Только после этого писать скрапер.

### 2. Написание src/scraper.js

Исследовать DOM/сетевую подгрузку сайта внутри подготовленного контейнера.
Установить достоверный сигнал конца ленты до фиксации алгоритма.
Не предполагать точное число цитат; отсутствие карточек за фиксированное время
не доказывает конец. Таймаут — ошибка. Неразрешённый сигнал конца — блокер
зависимой реализации.

Реализовать JSON-контракт, дедупликацию, ограниченные ожидания/общий таймаут,
закрытие браузера в `finally`. Перед новым запуском удалять предыдущий result,
новый записывать через временный файл и атомарную замену только после успеха.
Валидатор проверяет содержимое; свежесть обеспечивает порядок запуска,
удаление старого файла и успешный exit процесса.

Выполнить make build и make run для реального сайта. Отдельный набор тестов
и отдельная цель verify-result сейчас не требуются по уточнению пользователя.
Проверка результата встроена в ci на этапе 3. Замечания к скраперу сохраняются
в review-отчёте; изменение CI само по себе их не устраняет.

### 3. Завершение clean, ci, GitHub Actions и README

`clean` адресно удаляет образ проекта и out; отсутствие допустимо, реальные
ошибки видны. Не использовать prune, удаление builder или общий cache rm.
Не добавлять диагностические цели. Наличие образа проверяется внутри run;
состояние out, ignore-файлов и Git проверяется инспекцией репозитория.

`ci` последовательно вызывает build, run и запускает Node.js из собранного
образа для проверки out/result.json. Проверка находится прямо в рецепте ci,
отдельные цели test/verify-result не вызываются. Монтировать out только для чтения.
Требовать непустой массив объектов с непустыми строками text/author и массивом
строк tags. Отсутствующий файл, повреждённый JSON, пустой массив и неверные поля
должны давать ненулевой exit. Не объявлять этапы независимыми prerequisites: обеспечить
порядок и при make -j через цепочку зависимостей либо последовательные вызовы
`$(MAKE)`. Ошибка останавливает последующие этапы и возвращается вызывающей среде.

Workflow на push/PR: checkout и `make ci` на runner с Docker/Make.
Версии actions проверить по официальным источникам при реализации.
README описывает проект, формат результата, настройку среды разработки с Docker
и Make, контейнерную генерацию lockfile, сборку/запуск production-образа, clean
и проверку кеша. Все команды — через make. Node.js/Playwright/Chromium на хост
не устанавливаются. Не обещать проверку неподтверждённых ОС/архитектур.

### 4. Все восемь пунктов DoD и кеширование

Проверить каждый пункт по таблице Verification; PR и удалённый CI проверять
после отдельно разрешённой публикации. До этого отмечать их непроверенными,
не объявлять полный DoD выполненным.

Кеширование проверяется вручную через существующие цели Makefile,
без отдельного скрипта или цели автоматической проверки:

1. Выполнить `make build`, затем повторить `make build` и проверить `CACHED`
   у установки npm-зависимостей, системных библиотек и Chromium.
2. Выполнить `make clean`, затем `make build`: тяжёлые слои должны быть `CACHED`.
3. Вручную внести одну временную строку-комментарий в `src/scraper.js`,
   выполнить `make build` и проверить кеш тяжёлых слоёв.
4. Удалить только свой временный комментарий, сохранив остальные изменения,
   затем выполнить `make build`, чтобы образ соответствовал исходникам.

Не менять манифесты, builder и платформу между замерами. Если исходная сборка
уже использовала кеш, не выдавать её за доказательство первоначальной загрузки.
Не добавлять автоматическое изменение исходников для эксперимента.

После восстановления выполнить `make ci`, затем clean и сравнение Git baseline.
Записать реальные команды, cwd, exit и короткие выдержки логов в build-отчёт.
Обновить Memory Bank по завершённому этапу, сохранив требования лабораторной.

## Verification

Ниже предусмотренные проверки; фактические результаты хранятся в build-отчёте.
Рабочая директория — корень репозитория.

| Команда | Наблюдаемое свидетельство |
| --- | --- |
| `make lock`, затем `make build` | Lockfile создан контейнером, браузер установлен в образ, host Node не требуется |
| `make build`, затем `make run` | Образ собран, JSON появился на хосте |
| `make ci`, затем `make -j ci` | Сборка → запуск → встроенная проверка непустого JSON/схемы в контейнере; ошибки не теряются |
| Ручные `make clean` → `make build`; правка комментария → `make build` | Тяжёлые слои CACHED; временный комментарий удалён |
| `make clean` дважды и инспекция результата | Образ/out отсутствуют, кеш и исходные изменения сохранены |
| Просмотр workflow и статуса PR после разрешённой публикации | make ci; зелёный run на последнем SHA |

Сопоставление с восемью пунктами DoD задания:

| DoD | Проверка и свидетельство |
| --- | --- |
| 1 | PR feat/quotes-scrapper → main открыт и не слит; ссылка и состояние после разрешённой публикации |
| 2 | make build: exit 0, конечный образ существует |
| 3 | make ci: запуск и встроенная проверка подтверждают непустой валидный JSON на хосте |
| 4 | make clean: образ/out удалены; инспекция Git подтверждает чистоту на закоммиченном состоянии |
| 5 | Ручные make clean → make build: браузерный слой CACHED, загрузки нет |
| 6 | Ручная однострочная правка src/scraper.js → make build: npm/браузер/системные слои CACHED |
| 7 | Workflow вызывает make ci; зелёный GitHub run относится к последнему SHA PR |
| 8 | README содержит описание, настройку среды с Docker/Make и инструкции production-сборки |

Негативные сценарии ci проверять управляемым сбоем запуска/проверки результата: последующие
этапы не выполняются, старый JSON не даёт ложного успеха. Сетевой сбой или
недоступность Docker означают неуспешную/недоступную проверку, а не pass.
Отдельный постоянный набор тестов сейчас не входит в план. Разовые проверки
ошибок CI не заменяют проверку реального сайта и не означают покрытие сбоев скрапера.

## Risks and skeptic findings

Planner — основной агент. Отдельный агент skeptic проверил конкретный черновик
и файлы контекста. Его вердикт: revise; после включения MED-уточнения — proceed.
Контейнерная редакция по уточнению пользователя проверена основным агентом
как self-review; отдельная независимая проверка этой редакции не проводилась.

| Severity | Замечание | Разрешение |
| --- | --- | --- |
| LOW | По корректному JSON нельзя определить свежесть | Валидатор проверяет схему; свежесть обеспечивает жизненный цикл запуска |
| MED | Прежний порядок предполагал host-зависимости и скрапер до Docker | Контейнерный lock bootstrap и build/run предшествуют scraper.js; установка только внутри контейнеров |
| MED | COPY отсутствующего скрапера ломает первый build | На этапе 1 копируется существующий src с .gitkeep; run до этапа 2 ожидаемо неуспешен |

Риски исполнения: доступность сайта/registry, права bind mount на Linux,
несовпадение браузера и версии Playwright, изменение внешней страницы. Смена
builder/платформы или внешняя очистка кеша нарушают условия кеш-эксперимента.
Кеш между разными GitHub runner не требуется для проверки кеширования на одном builder.

## Blockers, assumptions and out of scope

Отсутствие test/verify-result больше не является блокером CI: его контракт
обновлён пользователем. Доступность Docker/сети проверяется при запуске;
результаты реализации и замечания к скраперу фиксируются в build/review-отчётах.

Допущения: полный обход, схема JSON, дедупликация и ESM — решения плана.
Число цитат заранее не задано. Полностью чистый Git DoD возможен после отдельно
разрешённых коммитов; существующие изменения не удалять ради проверки clean.

Текущий запрос разрешает изменение ci и согласование плана, README и Memory Bank
с проверкой make ci. Скрапер не менять. Коммиты, push, создание/слияние PR,
публикация образов, deploy и последующие лабораторные вне этого объёма.
Полный DoD лабораторной включает PR и удалённый CI и проверяется отдельно.
